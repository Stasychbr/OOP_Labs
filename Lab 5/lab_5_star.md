**Эксперимент с бэггингом kNN/NW заменяется сравнением двух семейств random

не требуется.** Добавляется важность исходных признаков методом перестановок.

Для своей задачи проводится полный эксперимент. Для второй задачи достаточно

## 1. Глубокие и мелкие леса

Сравните два семейства:

1. Глубокий лес: `max_depth` отсутствует или равен `null`; глубина не ограничена
   этим параметром, но остаются остальные условия остановки CART.
2. Мелкий лес: `max_depth` равен 2 или 3. При глубине корня 0 дерево имеет
   не более 4 или 8 листьев соответственно; фактическое число может быть меньше.

Используются одни и те же сохранённые train/test, конфиг предобработки,
стратифицированные фолды в классификации и метрика `scoring`. Обучение
предобработки выполняется внутри каждого фолда, как в основном условии.

Сделайте отдельные конфиги поиска для двух семейств. При полном переборе
пространство остальных параметров должно совпадать. При случайном поиске
используйте одинаковые пространства остальных параметров и одинаковые бюджеты;
фактически проверенные комбинации сохраняйте в результатах.

Пример небольшого поиска для глубокого леса:

```yaml
# configs/search_deep_forest.yaml
# Для регрессии: task: regression, scoring: mse.
task: classification
scoring: f1

model:
  type: random_forest
  params:
    max_depth: null
    n_estimators: 10
    max_features: sqrt
    min_samples_split: 2
    min_samples_leaf: 1
    bootstrap: true
    random_state: 42
    n_jobs: 2

cv:
  n_splits: 3
  random_state: 17

search:
  method: grid
  parameters:
    n_estimators:
      values: [5, 10]
    min_samples_leaf:
      values: [1, 3]
```

Для мелкого леса задайте фиксированное `model.params.max_depth: 2` и добавьте
в `search.parameters`:

```yaml
max_depth:
  values: [2, 3]
```

Это даёт 4 конфигурации глубокого и 8 мелкого леса, всего 36 обучений при трёх
фолдах. Размер сетки выбирает студент. Для долгих запусков разрешён простой
случайный поиск по правилам основного условия. Параллельный поиск не требуется;
`n_jobs` управляет только обучением элементов ансамбля через `std::jthread`.

`null` — значение YAML/JSON, а не строка `"null"`. Используйте уже поддержанные
деревом и лесом параметры. Пример не требует расширять модель за пределы работы 4.
**У разных деревьев одного леса должны быть разные воспроизводимо полученные
seed; один и тот же seed нельзя независимо присваивать каждому дереву.**


Выполните аналогичный запуск для мелкого леса. Лучшая конфигурация сохраняется
**отдельно внутри каждого семейства**. Не выбирайте единственного общего
победителя вместо двух результатов для сравнения.

Формат конкретного конфига совпадает с основным условием: `task`, `scoring`,
`model.type` и конкретные `model.params`, без `cv` и пространства поиска.
Фабрика расширяется типом `random_forest`; отдельный несовместимый формат
для звёздочки не нужен.

`evaluate_model` заново обучает предобработку и выбранный лес на всём train,
считает все метрики задачи на train/test и сохраняет тестовые предсказания.
Сравните CV и test, разрыв train/test и результаты двух семейств. Если доступно,
можно дополнительно показать число узлов/листьев и время обучения/предсказания;
специально реализовывать профилировщик не требуется.

Не предполагается, что мелкий лес обязательно лучше глубокого. Ограничение
глубины может как помочь, так и привести к недообучению.

## 3. Исходные признаки и обученная предобработка

Важность оценивается для **исходных признаков до one-hot кодирования**, а не
для отдельных столбцов готовой числовой матрицы. Для этого сохранённые train/test
должны содержать исходные значения и имена столбцов, как в основном условии.

Различайте два вида информации:

- конфиг предобработки задаёт способы преобразований: например, заполнение
  пропусков медианой и one-hot кодирование;
- обученный объект предобработки хранит вычисленные статистики, словари
  категорий и порядок выходных столбцов.

Одного числа категорий для каждого признака недостаточно. Для признака `color`
нужно знать, например, что `blue` соответствует одному выходному столбцу,
а `red` — другому. По имени исходного признака и сохранённому словарю должно
быть понятно, как он преобразуется. Не требуется хранить категориальные
словари в пользовательском конфиге: они восстанавливаются при `fit` на train.

После обучения словари и порядок столбцов фиксированы. Не перестраивайте их
по test или после перестановки признака. Определите поведение неизвестной
категории, например кодирование нулями или выделенной служебной категорией;
выберите один вариант и опишите его. Проверочная часть не должна расширять
словарь обучающей части фолда.

Для этой работы допустимо доработать интерфейс предобработки и представление
исходных данных. В README студенческого проекта поясните, что изменено и зачем.
Отдельный класс `Pipeline` по-прежнему необязателен: достаточно иметь доступ
к уже обученным предобработке и модели.

## 4. Permutation feature importance

Добавьте к `evaluate_model` флаг `--feature-importance` и параметры числа
повторений, seed и выходного файла:

```sh
evaluate_model \
  --train data/train.bin \
  --test data/test.bin \
  --preprocessing-config configs/preprocessing.yaml \
  --model-config results/best_deep_forest.yaml \
  --metrics-output results/deep_forest_metrics.csv \
  --predictions-output results/deep_forest_predictions.csv \
  --feature-importance \
  --importance-repeats 5 \
  --importance-random-state 123 \
  --importance-output results/deep_forest_importance.csv
```

Идея метода: перемешивание сохраняет набор значений признака, но разрушает
его соответствие конкретным объектам. Проверяем, насколько это ухудшает
предсказания уже обученной модели.

Выполните расчёт для обоих выбранных лесов. Важность считается на test после
итогового обучения. **Модель и предобработка при перестановках не переобучаются.**
Используется то же `scoring`, по которому выбирались конфигурации.

Алгоритм:

1. Один раз вычислите baseline — значение `scoring` на неизменённом test.
2. Для выбранного исходного признака и очередного повтора создайте рабочую
   копию исходного test либо восстановите её исходное состояние.
3. Перемешайте значения только этого признака между строками, включая пропуски,
   если они есть. Остальные признаки, отклики и порядок строк не меняются.
4. Примените **уже обученную** предобработку, получите предсказания того же леса
   и вычислите `scoring`.
5. Рассчитайте ухудшение относительно baseline. Повторите несколько раз.
6. Для признака сохраните среднее ухудшение и стандартное отклонение с делением
   на число повторений. Повторите для остальных исходных признаков.

Для максимизируемой метрики:

$$
I_{j,r}=score_{baseline}-score_{j,r}.
$$

Для минимизируемой:

$$
I_{j,r}=score_{j,r}-score_{baseline}.
$$

Здесь j — исходный признак, r — повтор перестановки. Используйте общий механизм
направления метрики; не фиксируйте отдельно MSE или F1 внутри алгоритма важности.

**Каждый повтор начинается с исходного test. Перестановки разных признаков
не должны накапливаться.** Можно использовать один генератор, созданный из
`importance-random-state`, и последовательно получать новые перестановки.
Не переинициализируйте его одним и тем же seed перед каждым повтором.
Случайное совпадение двух перестановок допустимо; намеренное повторение одной
из-за сброса генератора — ошибка.

При перестановке категориального признака его значение переносится целиком.
Например, перемешивается исходный `color`, а все связанные one-hot столбцы
затем согласованно получаются через `transform`. По отдельности столбцы
`color_red` и `color_blue` не перемешиваются.

Сохраните таблицу с именем исходного признака, средней важностью и разбросом,
отсортированную по убыванию средней важности. Например:

```text
Feature       Mean importance    Std
age                    0.0812    0.0061
income                 0.0475    0.0048
color                  0.0021    0.0017
```

Чем больше положительное ухудшение, тем сильнее перестановка этого признака
ухудшила качество модели на этой выборке. Нулевая и отрицательная важность допустимы: значения
не обрезаются и не скрываются. Важность зависит от модели, данных, метрики и
корреляций между признаками; она не доказывает причинное влияние. Слабая модель
может давать малоинформативные оценки важности.

Test здесь используется для окончательной оценки и интерпретации. После
просмотра метрик и важностей не удаляйте признаки и не перенастраивайте модель
с последующим объявлением нового результата на том же test независимой оценкой.

## 5. Место в проекте и проверки

Алгоритм важности не размещается внутри random forest: он должен работать
с обученным регрессором или классификатором и обученной предобработкой.
Достаточно функций в `evaluation` либо отдельного `feature_importance`.
Вход: исходные проверочные данные, отклики, обученные объекты, `scoring`, число
повторений и seed. Выход: записи с именем/индексом исходного признака,
средней важностью и разбросом. CLI только передаёт аргументы и сохраняет таблицу.

Каталоги и организация CMake рекомендуются в [README](README.md#рекомендуемая-структура-проекта).
Обязательна независимость ядра от CLI и будущего Qt, а не точное расположение
файлов.

К проверкам основного условия добавьте:

- baseline не пересчитывается после изменения данных;
- при перестановках нет вызовов `fit` модели и предобработки;
- исходные данные и отклики после расчёта не изменены;
- повтор для одного признака не затрагивает остальные;
- категориальный признак преобразуется с прежним словарём и порядком столбцов;
- знак важности корректен для минимизируемой и максимизируемой метрики;
- отрицательные значения сохраняются;
- одинаковый seed воспроизводит результаты.

Тесты разрешено писать с агентом. Сверка со scikit-learn необязательна и тоже
может выполняться с агентом; одинаковое число seed в разных реализациях не
обещает одинаковых bootstrap-выборок и перестановок.
